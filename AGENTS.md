# Musica: инструкции для работы с репозиторием

## Источники контекста

- Перед изменениями читайте относящуюся к задаче документацию:
  [backend](backend/DOCUMENTATION.md), [плеер](frontend-app/DOCUMENTATION.md),
  [профиль](frontend-admin/DOCUMENTATION.md).
- Храните здесь только правила работы. Описание архитектуры, поведения фич,
  API, конфигурации, запуска и развёртывания ведите в `DOCUMENTATION.md`
  соответствующего подпроекта; не дублируйте его в этом файле.

## Работа с кодом

- Не меняйте стек и не добавляйте крупные зависимости без необходимости для задачи.
- Сохраняйте независимые зависимости и сборки подпроектов. Не импортируйте
  исходники одного frontend в другой относительными путями.
- Размещайте исходники в `src/`, статические ресурсы frontend — в `public/`
  соответствующего подпроекта. Соблюдайте существующие границы модулей.
- Соблюдайте существующий стиль; форматируйте Zig через `zig fmt`.
- Импорты модулей других фич именуйте как `<feature>_<module>`:
  например, `auth_model`, `tracks_service`, `playlists_repository`.
  Для реализации в фасаде репозитория используйте имя `impl`.
- При изменении API согласованно обновляйте backend, frontend и документацию.
- При изменении настроек обновляйте примеры окружения, Compose, тесты и документацию.
- Сохраняйте lock-файлы frontend и закреплённые URL коммитов и хеши Zig-зависимостей.
  Не заменяйте зависимости локальными путями в манифесте.
- Проверяйте внешние данные во время выполнения: TypeScript-типы не валидируют JSON.
- Учитывайте время жизни памяти Zig: данные ответа должны жить до его отправки;
  для временных данных ответа используйте `res.arena`.
- Не записывайте секреты, локальную музыку, базы данных и артефакты сборки в Git.
- Проверяйте полномочия на backend; скрытие элементов интерфейса не заменяет
  проверку доступа. Не сохраняйте пароли и токены в localStorage и не передавайте
  их в URL. Проверяйте адрес возврата после авторизации.
- Обращайтесь к API по относительным URL под `/api/`.
- Не позволяйте service worker плеера перехватывать навигацию профиля.
- Для будущих файловых маршрутов проверяйте пути относительно медиатеки;
  не позволяйте клиенту читать произвольные файлы сервера.
- Не кешируйте приватные API-ответы и аудио service worker-ом без явного
  требования.
- Создавайте последовательные SQL-миграции в `backend/migrations/`.
  Не добавляйте автоприменение и не применяйте миграции к пользовательской БД
  без явного запроса.
- Учитывайте установку PWA, мобильные экраны, доступность и работу без сети.

## Стиль frontend и рефакторинг

- Используйте runes Svelte 5 и TypeScript strict. Передавайте состояние через
  context или props, без глобальных контроллеров и ручного рендера HTML.
- Разделяйте `app/`, `pages/`, `features/` и независимый `shared/`.
  В фичах используйте `model.ts` для DTO и валидации, `api.ts` для запросов,
  `state.svelte.ts` для состояния и `ui/` для компонентов по необходимости.
- Размещайте стили рядом с компонентами; общие переменные и базовые правила —
  в `shared/styles/`. Задавайте порядок подключения CSS в `app/styles.css`.
- Переводы храните в `shared/i18n/locales/ru-RU.ts` и `en-US.ts`.
  Используйте стабильные ключи и именованные параметры, не текст как ключ.
  Проверяйте английский словарь общим типом `Messages`.
- Сохраняйте поведение, API-контракты и оформление при рефакторинге.
  Перед удалением файлов, переименованиями и структурными изменениями сообщайте
  пользователю, что предлагается изменить и почему. Проверяйте использование
  файлов и символов, включая импорты стилей, тесты и динамическую загрузку.
- Пишите краткие русские JSDoc-описания (`/** ... */`) рядом с определениями
  функций, методов и существенных моделей. Описывайте назначение и важные
  условия: отмену запросов, повторы, защиту от устаревших ответов, частичное
  сохранение и освобождение ресурсов. Документируйте именованные обработчики
  компонентов; не пересказывайте очевидные строки и простые inline-callback.
  Храните документацию у реализации, не дублируйте её вручную в алиасах.
  Сохраняйте файлы в UTF-8 и проверяйте кириллицу после автоматических правок.
- Разделяйте импорты, объявления типов, функции и методы пустыми строками.
  В длинных функциях отделяйте логические этапы: проверку входа, подготовку
  состояния, запрос, проверку актуальности ответа и применение результата.
  Группируйте связанные поля классов перед методами; сохраняйте порядок
  инициализации полей и зависимости между ними.
- Имена функций и локальных переменных должны объяснять действие и назначение.
  Не добавляйте новые абстракции только ради сокращения строк. Повторяющиеся DTO
  храните в модели соответствующей фичи; в других местах используйте импорт
  типа или осмысленный алиас вместо копирования структуры.
- Компоненты отвечают за представление и пользовательский ввод, `api.ts` —
  за запросы и проверку ответов, состояния фич — за их сценарии. Согласуйте
  действия между фичами в `app/`. Выделяйте компоненты и модули по самостоятельной
  ответственности, сохраняя границы фич и независимость аудиодвижка от UI.
- Пишите CSS многострочными блоками и разделяйте правила пустыми строками.
  Группируйте основные стили и адаптивные правила; убирайте накопленные
  переопределения только с сохранением каскада, специфичности и итогового вида
  на ПК и мобильных экранах. Учитывайте обе темы и состояния hover/focus/disabled.
- При изменении асинхронного кода сохраняйте отмену и защиту от ответов прежнего
  запроса, трека или сессии. Различайте закрытие окна, сброс черновика и отмену
  уже запущенной операции. Освобождайте таймеры, слушатели, observers, object URL
  и аудиоресурсы в соответствующем жизненном цикле.

## Стиль backend и рефакторинг

- Используйте API Zig 0.16, включая `std.process.Init` и `std.Io`.
- Сервисы должны управлять соединением и транзакцией; репозитории — принимать
  готовое соединение без begin/commit/rollback. Не удерживайте соединение БД
  или транзакцию во время обращения к S3.
- Скрывайте драйвер, пул и SQLSTATE в infrastructure. Вне этого слоя используйте
  `Database`/`Connection`, не импортируйте `pg` и не размещайте SQL.
  Выполняйте запросы репозиториев через `Connection.queryText/exec`.
- Явно указывайте схемы в SQL: `public.jobs` для заданий, `musica` для остальных
  таблиц и типов приложения. Не добавляйте поля конкретных фич в общую jobs:
  храните их в payload, а схемы и обработчики — в фичах.
  При продлении и завершении проверяйте attempt_id и действующую аренду по часам БД.
- Сохраняйте поведение при рефакторинге оформления и названий. Изменение имени
  обработчика не означает изменение URL, HTTP-метода или контракта ответа.
  Обновляйте все ссылки на переименованный символ, включая фасады и тесты.
- Разделяйте функции, объявления типов и реэкспорты пустой строкой. Внутри
  длинной функции отделяйте смысловые этапы: проверку входа, получение данных,
  внешнюю операцию и формирование результата. Длинные сигнатуры, вызовы,
  инициализаторы и SQL оформляйте многострочно; не уплотняйте код в одну строку.
- Пишите краткие русские `///`-описания функций, моделей и важных полей рядом
  с их определением. Описывайте назначение и существенные условия: блокировку,
  аренду, транзакцию, владение ресурсом или время жизни памяти. Для Python
  используйте краткие docstring. Не пересказывайте очевидные строки реализации.
- Документацию функций репозитория храните в infrastructure-реализации.
  Фасад с `pub const ... = impl...` не должен вручную дублировать её.
  Не добавляйте общие `//!`-шапки, повторяющие правила слоёв из этого файла.
  Сохраняйте текст в UTF-8 и проверяйте кириллицу после автоматических правок.
- Имена функций должны выражать действие. В контексте репозитория допустимы
  `create`, `update`, `remove`; для неоднозначных операций используйте названия
  вроде `setImage`, `setLink`, `lockForUpload`, `lockForDeletion`. Префикс `lock`
  должен соответствовать реальной блокировке, а не обычному чтению.
  Сообщайте о предлагаемых переименованиях и кратко объясняйте их смысл.
- Файл моделей фичи называется `model.zig`. Не повторяйте название фичи в
  каждом типе, если контекст уже понятен: `tracks_model.Status`,
  `tracks_model.Files`, `streaming_model.State`, `Payload`, `Task`.
  Уточняйте имя, когда в одном модуле есть несколько сущностей, например
  `CreateTrack`, `UploadPayload`, `CleanupPayload`. Сохраняйте понятные имена
  локальных переменных и импортов вместо неочевидных сокращений.
- Соблюдайте границы routes/model/service/repository: HTTP и общий перевод
  ошибок — через routes и `helpers/api.zig`, бизнес-операции — в service,
  SQL — в infrastructure. В Release скрывайте ошибки БД и S3 из ответов,
  сохраняя диагностику в логах. Используйте общий `api.failure` для ошибок,
  уже представленных в общей модели, вместо повторяющихся ручных ответов.
- Хешируйте пароль до получения соединения через общий helper.
  Сохраняйте атомарность создания пользователя и сессии при регистрации.
- Выделяйте совместные операции в `operations.zig`, если они должны выполняться
  в транзакции вызывающего сервиса. Не расширяйте сервис парой публичных функций,
  отличающихся только наличием собственной транзакции.
- В тестах сохраняйте проверку поведения: прав доступа, отката, повторов,
  аренды и завершения устаревших попыток. Переиспользуйте `backend/tests/support.py`;
  ожидания ограничивайте таймаутом с диагностикой последнего состояния.
  Интеграционные тесты используйте с отдельной временной
  БД и не должны зависеть от локальных настроек стартового администратора.

## Проверка изменений

- Frontend: в каждом изменённом подпроекте (`frontend-app/`, `frontend-admin/`)
  выполните `npm ci`, затем `npm run build`.
  Сборка включает `svelte-check`. Проверяйте формат через `npm run format:check`.
  В обоих подпроектах проверяйте локализацию через `npm run test:i18n`.
  В `frontend-app/` для логики используйте `npm run test:player` и `npm run test:spotify`,
  для аудионастроек — `npm run test:audio`, для Web-поиска — `npm run test:web`
  и `npm run test:web-ui`, для локализации — `npm run test:i18n`,
  для интерфейса — `npm run test:ui`, для прокси — `npm run test:proxy`,
  для production service worker — `npm run test:pwa`.
- Backend: из `backend/` выполните `zig fmt --check build.zig src`, затем `python3 build.py`.
  Для логики backend запускайте также `python3 build.py test`.
  На Windows используйте `python` вместо `python3`.
  Не пересобирайте проект после каждой промежуточной правки: выполняйте
  необходимые проверки после завершения согласованной серии изменений.
- Для изменений HTTP запускайте `python3 build.py run` и проверяйте затронутые маршруты.
- Проверяйте production PWA через `npm run preview` с reverse proxy для API.
- Добавляйте содержательные тесты для новой логики и исправлений ошибок.
  Не создавайте тесты, которые лишь повторяют конфигурацию или реализацию.
- Для правок только документации сборка не требуется.
- Если проверка недоступна, явно сообщите причину; не называйте её пройденной.
