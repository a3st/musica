# Musica: инструкции для работы с репозиторием

Musica — self-hosted музыкальный плеер. Репозиторий содержит два независимых
подпроекта: `frontend/` и `backend/`.

## Стек и границы

- Frontend: Svelte 5, TypeScript в strict-режиме, Vite, PWA через vite-plugin-pwa.
  `src/app/` собирает приложение, `src/pages/` компонует страницы,
  `src/features/` содержит фичи, `src/shared/` — общие независимые модули.
  В фиче используйте `model.ts` для DTO и валидации, `api.ts` для запросов,
  `state.svelte.ts` для реактивного состояния и `ui/` для компонентов.
  Используйте runes Svelte 5; состояние приложения передавайте через context
  или props, без глобальных экземпляров контроллеров и ручного рендера HTML.
  Audio/HLS движок отделён от интерфейса; освобождайте слушатели, таймеры,
  запросы и ресурсы при завершении соответствующего жизненного цикла.
  Пишите CSS многострочными блоками. Стили компонентов размещайте рядом
  с компонентом; общие переменные и базовые правила — в `shared/styles/`.
  Порядок подключения внешних CSS задаётся в `app/styles.css`.
  Переводы размещайте в `shared/i18n/locales/ru-RU.ts` и `en-US.ts`.
  Используйте стабильные ключи (`uploads.title`) и именованные параметры
  через `t('tracks.play', { title })`. Не используйте текст как ключ.
  Английский словарь должен удовлетворять общему типу `Messages`;
  проверяйте локализацию через `npm run test:i18n`.
- Backend: Zig **0.16.0**, HTTP-сервер karlseguin/http.zig (модуль `httpz`).
  Используйте API Zig 0.16, включая `std.process.Init` и `std.Io`.
- БД: PostgreSQL через pg.zig; файлы: MinIO через S3. Настройки передаются
  окружением, примеры — `backend/.env.example`.
  Настройки подключения приложения называются `DB_HOST`, `DB_PORT`, `DB_NAME`,
  `DB_USER`, `DB_PASSWORD`. В Compose преобразуйте их в `POSTGRES_*` для
  контейнера PostgreSQL; стандартные переменные `psql` относятся к самому `psql`.
  При изменении настроек обновляйте примеры окружения, Compose, тесты и README.
- Backend организован по фичам в `backend/src/features/`: routes (HTTP),
  model (DTO/валидация), service (операции), repository (API хранения).
  Реализации репозиториев и SQL находятся в `backend/src/infrastructure/repositories/`.
  Сервисы получают и освобождают `Connection`, управляют begin/commit/rollback;
  репозитории принимают готовое соединение и не управляют транзакциями.
  Не удерживайте соединение или транзакцию БД во время обращения к S3.
  Общая модель Job и репозиторий таблицы jobs находятся в `infrastructure/jobs/`.
  Таблица размещается в public; в SQL репозитория всегда указывайте `public.jobs`.
  Остальные таблицы, enum и функция триггера размещаются в musica;
  в запросах к таблицам приложения явно указывайте схему `musica`.
  Не добавляйте в jobs поля конкретных фич: их данные храните в payload, схемы
  и обработчики — в фичах. Продление и завершение требуют совпадения attempt_id
  и действующей аренды; проверяйте сроки по часам БД.
  Драйвер БД, пул, соединения, настройки подключения и перевод SQLSTATE скрыты
  в `backend/src/infrastructure/database.zig`. Вне infrastructure используйте
  `Database`/`Connection`; не импортируйте `pg` и не размещайте PostgreSQL-запросы.
  Общие вспомогательные функции HTTP размещайте в `backend/src/helpers/`.
  Запросы в infrastructure-репозиториях выполняйте через `Connection.queryText/exec`.
- SQL-миграции размещайте в `backend/migrations/` с последовательными номерами.
  Начальная схема для пустой БД находится в `001_init.sql`.
  Пользователь выполняет их вручную: не добавляйте автоприменение при запуске
  и не применяйте их к пользовательской БД без явного запроса.
- Не меняйте стек и не добавляйте крупные зависимости без необходимости для задачи.
- API размещается под `/api/`; frontend обращается к нему по относительным URL.
  В разработке запросы проксирует Vite, в production — reverse proxy.
- Сохраняйте воспроизводимость: коммитьте `frontend/package-lock.json` и
  `backend/build.zig.zon` с URL конкретного коммита и хешами зависимостей.

## Работа с кодом

- Размещайте клиентский код в `frontend/src/`, статические ресурсы в
  `frontend/public/`, серверный код в `backend/src/`.
- Соблюдайте существующий стиль; форматируйте Zig через `zig fmt`.
- Импорты модулей других фич именуйте как `<feature>_<module>`:
  например, `auth_model`, `tracks_service`, `playlists_repository`.
  Для реализации в фасаде репозитория используйте имя `impl`.
- При изменении API согласованно обновляйте backend, frontend и документацию.
- Проверяйте внешние данные во время выполнения: TypeScript-типы не валидируют JSON.
- Учитывайте время жизни памяти Zig: данные ответа должны жить до его отправки;
  для временных данных ответа используйте `res.arena`.
- Не записывайте секреты, локальную музыку, базы данных и артефакты сборки в Git.
- Для будущих файловых маршрутов проверяйте пути относительно медиатеки;
  не позволяйте клиенту читать произвольные файлы сервера.
- Не кешируйте приватные API-ответы и аудио service worker-ом без явного
  требования. Сейчас PWA кеширует только оболочку приложения.
- Учитывайте установку PWA, мобильные экраны, доступность и работу без сети.

## Стиль backend и рефакторинг

- Сохраняйте поведение при рефакторинге оформления и названий. Изменение имени
  обработчика не означает изменение URL, HTTP-метода или контракта ответа.
  Обновляйте все ссылки на переименованный символ, включая фасады и тесты.
- Разделяйте функции, объявления типов и реэкспорты пустой строкой. Внутри
  длинной функции отделяйте смысловые этапы: проверку входа, получение данных,
  внешнюю операцию и формирование результата. Длинные сигнатуры, вызовы,
  инициализаторы и SQL оформляйте многострочно; не уплотняйте код в одну строку.
- Пишите краткие русские `///`-описания функций, моделей и важных полей рядом
  с их определением. Описывайте назначение и существенные условия: блокировку,
  аренду, транзакцию, владение ресурсом или время жизни памяти. Для Python
  используйте краткие docstring. Не пересказывайте очевидные строки реализации.
- Документацию функций репозитория храните в infrastructure-реализации.
  Фасад с `pub const ... = impl...` не должен вручную дублировать её.
  Не добавляйте общие `//!`-шапки, повторяющие правила слоёв из этого файла.
  Сохраняйте текст в UTF-8 и проверяйте кириллицу после автоматических правок.
- Имена функций должны выражать действие. В контексте репозитория допустимы
  `create`, `update`, `remove`; для неоднозначных операций используйте названия
  вроде `setImage`, `setLink`, `lockForUpload`, `lockForDeletion`. Префикс `lock`
  должен соответствовать реальной блокировке, а не обычному чтению.
  Сообщайте о предлагаемых переименованиях и кратко объясняйте их смысл.
- Файл моделей фичи называется `model.zig`. Не повторяйте название фичи в
  каждом типе, если контекст уже понятен: `tracks_model.Status`,
  `tracks_model.Files`, `streaming_model.State`, `Payload`, `Task`.
  Уточняйте имя, когда в одном модуле есть несколько сущностей, например
  `CreateTrack`, `UploadPayload`, `CleanupPayload`. Сохраняйте понятные имена
  локальных переменных и импортов вместо неочевидных сокращений.
- Соблюдайте границы routes/model/service/repository: HTTP и общий перевод
  ошибок — через routes и `helpers/api.zig`, бизнес-операции — в service,
  SQL — в infrastructure. В Release скрывайте ошибки БД и S3 из ответов,
  сохраняя диагностику в логах. Используйте общий `api.failure` для ошибок,
  уже представленных в общей модели, вместо повторяющихся ручных ответов.
- Совместные операции над треками и плейлистами размещайте в
  `features/tracks/operations.zig`, когда нужно работать в транзакции вызывающего
  сервиса. Не расширяйте сервис парой публичных функций, отличающихся только
  наличием собственной транзакции. Очистка файлов треков остаётся в tracks;
  общая инфраструктура jobs хранит задачу, а её смысл и обработку задаёт фича.
  Создание и дедупликация общих треков у сервисной учётки, очередь скачивания
  и запуск yt-dlp относятся к `imports`. Web и Spotify используют её сервис;
  поиск сервисных треков и работа с каталогом остаются в `web_int`.
  Публикация файлов в S3, метаданные и очистка файлов остаются в `tracks`.
  Imports работает только при одновременно включённых Web и Spotify;
  выключение любой интеграции запрещает создание задач и запуск worker.
  `tracks.searchLibrary` ищет пользовательские треки в доступных плейлистах;
  `web_int.search` ищет загруженные сервисные треки и каталог, возвращает оба набора
  без повторов по источнику или исполнителю и полному названию. Проверку доступа
  выполняет backend, а не только frontend.
- В тестах сохраняйте проверку поведения: прав доступа, отката, повторов,
  аренды и завершения устаревших попыток. Общие Python-помощники находятся
  в `backend/tests/support.py`; ожидания ограничивайте таймаутом с диагностикой
  последнего состояния. Интеграционные тесты используют отдельную временную
  БД и не должны зависеть от локальных настроек стартового администратора.

## Проверка изменений

- Frontend: из `frontend/` выполните `npm ci`, затем `npm run build`.
  Сборка включает `svelte-check`. Проверяйте формат через `npm run format:check`.
  Для логики используйте `npm run test:player` и `npm run test:spotify`,
  для интерфейса — `npm run test:ui`, для прокси — `npm run test:proxy`,
  для production service worker — `npm run test:pwa`.
- Backend: из `backend/` выполните `zig fmt --check build.zig src`, затем `zig build`.
  Для логики backend запускайте также `zig build test`.
  Не пересобирайте проект после каждой промежуточной правки: выполняйте
  необходимые проверки после завершения согласованной серии изменений.
  Для правок только документации сборка не требуется.
- Для изменений HTTP запускайте `zig build run` и проверяйте затронутые маршруты.
  Начальный контракт: `GET /api/health` → `200`, JSON
  `{"status":"ok","service":"musica"}`; неизвестный маршрут → `404`.
- Проверяйте production PWA через `npm run preview`: service worker по умолчанию
  отключён в dev. Для полноценной проверки API нужен reverse proxy с `/api/`.
- Добавляйте содержательные тесты для новой логики и исправлений ошибок.
  Не создавайте тесты, которые лишь повторяют конфигурацию или реализацию.
- Если проверка недоступна, явно сообщите причину; не называйте её пройденной.
