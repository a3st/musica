# Frontend Musica

TypeScript strict, Vite, DOM API, PWA. Интерфейс работает с настоящим API
по относительным URL `/api/`; демонстрационных треков в приложении нет.

## Запуск

Сначала настройте backend, PostgreSQL, MinIO и вручную примените `001_init.sql`
к пустой БД по [инструкции backend](../backend/README.md). Для воспроизведения включите HLS-воркер
и установите FFmpeg на backend либо используйте Docker-образ.

Из `frontend/`:

```sh
npm ci
npm run dev
```

В PowerShell при запрете `npm.ps1` используйте `npm.cmd`.
Откройте <http://localhost:5173>. Vite проксирует `/api` на `127.0.0.1:8080`.
Прокси сохраняет исходный `Host` (`changeOrigin: false`), чтобы он совпадал
с браузерным `Origin` при проверке изменяющих cookie-запросов на backend.
Вход и регистрация создают HttpOnly cookie-сессию; токен не сохраняется
в localStorage и не добавляется в URL аудио.

## Интерфейс

- На ПК слева находится список собственных и общих плейлистов. На мобильном
  его открывает кнопка библиотеки рядом с поиском.
- Поиск фильтрует текущий плейлист по названию и исполнителю.
- Плеер снизу показывает обложку текущего плейлиста, название и исполнителя.
  Есть пауза, следующий/предыдущий трек, перемотка; на ПК также громкость,
  случайный порядок и повтор. Пробел управляет воспроизведением вне форм.
- Кнопка загрузки доступна на ПК. Можно выбрать несколько файлов или
  перетащить их в окно, поправить название и исполнителя, выбрать плейлист.
  Все треки также попадают в `Uploads`. Лимит клиента — 64 MiB на файл,
  до 50 файлов в очереди. Backend может установить меньший лимит.
- Для каждого файла выполняются создание трека, PUT файла и подготовка HLS.
  Есть прогресс, отмена текущей загрузки и повтор ошибки. Можно закрыть окно:
  очередь продолжит работать, пока открыта вкладка. Перезагрузка страницы
  сбрасывает очередь; незавершённые записи остаются в `Uploads` для удаления.
- Меню трека позволяет добавить его в другой доступный для записи плейлист
  и удалить. Из `Uploads` удаляется запись, все связи, оригинал и опубликованный
  HLS; из обычного плейлиста — только связь. Перед удалением показано подтверждение.
  Во время подготовки HLS backend отклоняет полное удаление с `409`.
- Плейлист можно создать с названием, описанием и видимостью. Общие плейлисты
  отображаются с учётом роли; viewer не может менять состав.

Safari использует нативный HLS, остальные поддерживаемые браузеры — `hls.js`,
загружаемый при первом воспроизведении. Приватные запросы манифеста и сегментов
авторизуются cookie-сессией. Если autoplay заблокирован, нажмите кнопку плеера.
Прослушивание без сети пока недоступно.

## Production и PWA

```sh
npm run build
npm run preview
```

Результат — `dist/`. Для production разместите его в корне домена за HTTPS
и проксируйте `/api/` к backend на том же домене. Передавайте исходный `Host`
и задайте backend `AUTH_COOKIE_SECURE=true`. `preview` нужен только для проверки
сборки; для API в этом режиме нужен reverse proxy.

Service worker кеширует оболочку, включая код HLS-клиента, но не API,
обложки из API или аудио. Обновление применяется по кнопке; активная загрузка
откладывает его. В dev service worker отключён. Манифест позволяет установить
приложение на домашний экран/рабочий стол.

## Импорт Spotify

Кнопка **Импорт из Spotify** находится в боковой медиатеке, в том числе на мобильном.
Выберите `Playlists.json`, `YourLibrary.json` или оба файла из выгрузки аккаунта Spotify.
До отправки отображается количество уникальных треков и плейлистов. Подкасты и
локальные файлы пропускаются; неверный JSON и метаданные показывают ошибку.

Плейлисты создаются приватными, все треки попадают также в Uploads. Совпадения по
Spotify URI объединяются в рамках одного импорта; без URI используется название
и исполнитель. Повторный импорт создаёт новые записи. Скачивание продолжается
на сервере после закрытия окна. Окно показывает очередь, скачивание, подготовку
и ошибки; неудачные задания можно повторить. Поиск по названию и исполнителю
может подобрать другую версию композиции. Обложка встраивается в MP3,
а интерфейс плеера пока показывает обложку плейлиста.
ID последнего импорта сохраняется отдельно для каждого пользователя, чтобы
показать его прогресс после перезагрузки страницы; метаданные треков не кешируются.

## Проверки

```sh
npm run check
npm run test:spotify
npm run build
npm run test:proxy
# В другом терминале уже запущен npm run dev:
npm run test:ui
# После сборки, в другом терминале запущен npm run preview:
npm run test:pwa
```

Браузерные тесты используют Playwright и изолированный API из фикстур,
пользовательская БД не затрагивается. FFmpeg должен быть в PATH или указан
через `FFMPEG_PATH`: он генерирует настоящее аудио для проверки HLS.
На Windows автоматически используется установленный Microsoft Edge.
На остальных системах установите Chromium командой `npx playwright install chromium`
либо задайте путь через `CHROMIUM_PATH`. `UI_TEST_URL` меняет адрес тестируемого
frontend, по умолчанию `http://127.0.0.1:5173`.
`test:pwa` по умолчанию обращается к `http://127.0.0.1:4173` и проверяет
production service worker, содержимое кеша и открытие оболочки без сети.
`test:proxy` запускает настоящий Vite-прокси с временным HTTP-приёмником
и проверяет передачу Host/Origin/cookie для создания плейлиста и загрузки;
работающий backend и браузер для него не нужны.

Проверяются размеры ПК/мобильного, поиск, безопасный вывод метаданных,
воспроизведение, очередь загрузки, создание плейлиста, вход и оба удаления.
Скриншоты сохраняются в игнорируемый `backend/.zig-cache/`.
